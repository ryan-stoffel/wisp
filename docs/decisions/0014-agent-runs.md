## Context

M3's done-when is one subagent that completes a task in a worktree and writes to shared context. #156 ties together the backends (#113, #116), routing (#119, 0012), the worker sandbox (#137, 0013), worktrees (#154, #166), shared context (#155, 0005), usage (#120), and the protocol (0007, 0011). 0007 sketched the `agents` capability's methods and events. Building them settled names and behavior that the editor (#105, #157) and the environment question (#96) depend on.

## Decision

### Protocol, behind the `agents` capability

| Method | Params | Result |
| --- | --- | --- |
| `agent/start` | `{runId, project, prompt, policy: "workspaceWrite", account?, model?, effort?, permission?}` | `{run}` |
| `agent/send` | `{runId, turnId, text, model?, effort?, permission?}` | `{run}` |
| `agent/cancel` | `{runId}` | `{run}` |
| `agent/list` | `{project?}` | `{runs, seq}` |
| `agent/events` | `{runId, after, limit?}` | `{events, more}` |

- `agent/cancel` is 0007's `agent/stop`, named as #156 asks. `agent/events` replaces 0007's `agent/output`: it pages through all of one run's logged events, not only output, which is what an editor needs to rebuild a transcript after `resyncRequired` or a restart.
- `agent/start` is idempotent on `runId` (0007). A retry with the same project, prompt, policy, account, model, effort, and permission returns the run; different params fail with `idConflict`. `account` absent means the worker role's default (0012).
- `model`, `effort`, and `permission` (RYA-97) are sent only to a plxd that advertises the `runOptions` capability, since an older one would ignore them (0007). Each is optional, and absent means the CLI's default. `model` is the backend's own name, such as `opus`. `effort` is `low`, `medium`, `high`, `xhigh`, or `max`. `permission` is `edit` (the default: edits and commands without asking) or `plan` (Claude Code's plan mode, whose file tools refuse to write). Both permissions run inside the worker sandbox (0013); nothing loosens it. The run stores all three, reports them on `AgentRun`, and passes them again when it resumes. A backend lists the efforts and permissions it maps (`Backend::efforts`, `Backend::permissions`, none by default), and anything else, or a model name that can't be a CLI argument, fails with `unsupportedOption` before anything is created. Claude Code maps them to `--model`, `--effort`, and `--permission-mode acceptEdits` or `plan`. Codex maps `model` to `-m` and `effort` to `-c model_reasoning_effort`, and takes only `edit`, since `codex exec` has no plan mode (RYA-38). plxd can't check a model name against the vendor's list, so an unknown model fails the run with the CLI's own error.
- `agent/send` is idempotent on `turnId` while plxd runs. It goes to a running CLI as its next turn, once the turn in progress ends ([0048](0048-durable-queue-and-steer.md)), or with `delivery: steer` into that turn. Once the run's CLI has ended, it resumes the vendor session in the same worktree with the message as the prompt (0011: Ryan messages a subagent directly).
- `agent/send`'s `model`, `effort`, and `permission` (RYA-161, RYA-163) change the run's. `effort` and `permission` are sent only to a plxd that advertises the `sendOptions` capability, and `model` only to one that advertises its successor `sendModel`, since a plxd without it would silently ignore it (the app gates all three on `sendModel`). A model should be one the run's backend runs, or the new account's. plxd can't check a model name against a backend, so another provider's model on the run's own backend fails the run with the CLI's own error. Absent, or equal to the run's, they change nothing. Otherwise plxd checks them against the run's backend as `agent/start` does, stores them on the run, and resumes the CLI with them.
- `agent/send`'s `account`, behind `sendAccount`, moves a run to another account, so a thread or a coordinator isn't tied to the provider it started on. On the run's backend, the session resumes on it. A session can't move to another CLI, so on another backend plxd starts a new session in the run's worktree (a coordinator's, in the project's repository), whose first message is the run's usual first message with the conversation so far in place of the task: the user's messages, Parallax's wake-ups, and the agent's replies, without tool calls, whose work is in the folder, cut from the front to about 64 KiB. The run keeps its id, transcript, worktree, and branch, and takes the new backend, the message's model (another vendor's can't carry over), and its effort and permission where the new backend maps them. A run with no session to resume can also be moved this way. If the new CLI doesn't start, the run moves back. The transcript notes the move, and `agent.updated` reports `backend`. A coordinator can only move to a backend that can run one (0024).
- A running CLI can't take a new model, effort, permission, or account, so with `sendAccount` such a message waits, in order with every message sent after it, until the CLI exits; then each starts a CLI of its own, as a message to a finished run does. A backend that takes no messages while it runs gets them the same way. A waiting message that can't be sent is dropped with `followUpDropped` and a warning saying why, and `agent/cancel` drops every waiting message. Waiting messages are stored, and a restart sends them ([0048](0048-durable-queue-and-steer.md)). A plxd without `sendAccount` refuses a changing message while the CLI runs with `unsupportedOption`.
- Events, all project-scoped and all carrying `runId`: `agent.started {run?}` (plxd always sends `run`; it is optional only because a v1 sample predicted `agent.started {runId}`), `agent.updated {state}` with only the fields that change during a run (status, account, session, error, diff, model, effort, permission, `updatedAt`; never the prompt), `agent.output {items}` coalesced per run every 50 ms, `agent.accountFallback`, `agent.finished {outcome}` once per CLI process, and `agent.diffReady {diff}` after each commit.
- Errors: `runNotFound`, `runNotResumable`, `workerUnavailable` (a backend without 0013, a missing or too old CLI with both versions named, a sandbox path holding `*?[]`), `worktreeFailed` (for example a path that isn't a repository, or a git failure; #257 stopped counting the repository's own uncommitted changes as one), and `unsupportedOption` (RYA-97).

### A run's life

- **Statuses:** `starting`, `running`, `completed`, `failed`, `cancelled`, `interrupted`. A run outlives its CLI processes: `completed`, `failed`, `cancelled`, and `interrupted` runs with a session id take `agent/send`.
- **Before anything is created,** plxd resolves the account (`routing::resolve`, `Role::Worker`), refuses a backend whose `Capabilities::worker_sandbox` is false, checks Claude Code's or Codex's detected version against its backend's `WORKER_MIN_VERSION`, canonicalizes and checks every sandbox path, and checks the run's model, effort, and permission against the backend. Detection reads the version from `claude --version` when `claude auth status` doesn't report one.
- **Then** it creates the worktree, records the run and worktree rows in one transaction (with #166's pinned `git_dir`), and starts the CLI with `WorkerSandbox::for_worktree`, whose git folder comes from the user's own checkout. The first prompt tells the agent its limits (0013).
- **One actor task per run** takes commands and backend events in one loop. It charges usage to the run's current account, which changes on `AccountFallback` (0012).
- **When a CLI process ends,** plxd commits the worktree on the run's branch with `commit_all` (#166: pinned git folder, no hooks), whatever the outcome, and reports the commit's stats against the worktree's base. A failed commit fails the run with `commitFailed`.
- **When plxd stops,** it cancels running CLIs and records their runs `interrupted`, without committing. **When plxd starts,** any run still `starting` or `running` (a crash) becomes `interrupted`. Both resume through `agent/send` by their session id, on the account the session ended on (after any fallback), not the worker role's current default; if that account is gone, or now runs on another backend, `agent/send` fails with `runNotResumable`.

### Review and accept (#157, #68)

Added by #157, behind a new `agentReview` capability. What a client reviews is exactly what Accept merges: the run's latest commit (`run.diff.commit`) against its worktree's base. The uncommitted edits of a running agent can't be reviewed; plxd commits them when its CLI ends.

| Method | Params | Result |
| --- | --- | --- |
| `agent/diff` | `{runId}` | `{base, head, files, stats, truncated}`: per file its status, stats, and a unified diff capped at 256 KiB, with 4 MiB in all, 2 MiB of file list, and 3,000 files listed. Caps count JSON-escaped size, so the answer fits 0007's 8 MiB frame |
| `agent/file` | `{runId, path, side: "base" \| "head", sizeOnly?}` | `{commit, exists, size?, content?, tooLarge}`: base64 content, capped at 4 MiB; `sizeOnly` leaves it out, for a file system's `stat` |
| `agent/accept` | `{runId, id, commit?}` | `{run, merge: {commit, into, how: fastForward \| merge \| upToDate}}` |
| `agent/requestChanges` | `{runId, turnId, text}` | `{run}`, sent as `agent/send` sends a message |
| `agent/openPr` | `{runId, title, body?}` | `{url}`, behind the `openPr` capability (RYA-168) |
| `agent/gitStatus` | `{runId}` | `{branch, changes, upstream, ahead, origin}`, behind the `git` capability (RYA-298) |
| `agent/commit` | `{runId, message}` | the status after the commit, behind `git` |
| `agent/push` | `{runId}` | the status after the push, behind `git` |
| `agent/files` | `{runId, path?}` | `{entries: [{name, kind: file \| dir \| symlink, size?}], truncated}`: one folder of the run's files on disk, behind the `files` capability (RYA-296) |
| `pr/view` | `{runId, url}` | `PullRequest`: one of the run's linked pull requests from `gh pr view`, behind the `pullRequests` capability (PLX-318) |
| `pr/act` | `{runId, url, action: merge \| squash \| autoMerge \| disableAutoMerge \| draft \| ready \| close}` | the `PullRequest` after the action, behind `pullRequests` |

- **Reads** come from git's objects (`ls-tree` and `cat-file` on the commit), through #166's pinned and hardened worktree calls, and never from the worktree's files. So a symlink comes back as its target text and is never followed, and a path through a symlinked folder doesn't exist. `path` must be relative, with no empty, `.`, or `..` component, no backslash or NUL, and nothing under `.git`, and it is matched literally.
- **Browsing** (RYA-296), behind the `files` capability, reads the run's folder on disk: its worktree, or a Current checkout thread's checkout. `agent/files` lists one folder by name, at most 5,000 entries, leaving out `.git` and whatever `git check-ignore` reports (except inside a submodule or nested repository, whose folders list everything, since `check-ignore` fails there), and `agent/file`'s `working` side reads one file as it is now, with no `commit` and the same 4 MiB cap. `path` follows the rules above. Neither follows a symlink: a symlink is listed as one and read as its target text, and a path through a symlinked folder is refused. A coordinator has no folder to browse.
- **Git's file lists are read whole or not at all** (RYA-143). A `-z` list, such as a commit's changed files or `git status`, has no newline, so it is one line. plxd reads a git line of up to 64 MiB, about 800k paths. A longer one fails the call, so `agent/diff` fails with `worktreeFailed` and Accept refuses with `mergeRefused`, rather than either acting on an empty list.
- **Accept** (#68's default) merges the run's commit into the current branch of the project's checkout on the host, and never pushes. It refuses, with nothing changed (`mergeRefused`), when the run is running or has no commit, when HEAD is detached, when a merge, rebase, cherry-pick, revert, or am is in progress, when uncommitted changes (staged, unstaged, or untracked) touch a path the merge changes, when any file, ignored ones included, sits where the merge adds one, or when `commit` isn't the run's latest commit. When the branch has moved on, `git merge-tree --write-tree` builds the merge in the object store, a conflict refuses with `mergeConflict` and names the files, and a clean result becomes an unsigned merge commit. The branch and working tree then move with `git merge --ff-only --no-overwrite-ignore <result>`, which keeps unrelated uncommitted changes and never overwrites an ignored file such as `.env`. Then plxd removes the worktree and branch, records the run `accepted`, and emits `agent.accepted {runId, merge}` and `agent.updated`. `id` makes a retry after a lost connection return the same answer, even after a restart. An accepted run fails `agent/diff`, `agent/file`, and `agent/send` with `runAccepted`.
- **Open PR** (RYA-168) is the other way to land a run: through the run's actor, as Accept is, it refuses a running run, one with no commit, and a thread with no repo, whose scratch repository has no `origin` (`prRefused`), then in the user's checkout, as the user, pushes the run's branch to `origin` (`pushFailed`, with git's stderr, when there is no `origin` or the push fails) and asks `gh`, found on the same `PATH` as the agent CLIs, for the branch's open pull request in `origin`'s own repository (not a fork's), opening one against the GitHub repository's default branch if there is none. So a retry pushes new commits and returns the same pull request. A missing or signed-out `gh` is `ghUnavailable`, and any other `gh` failure `prFailed`, each with its stderr. The push runs no hooks and never prompts, like every git call plxd makes; an `origin` reached over SSH can't use an SSH agent, since no process plxd starts gets `SSH_AUTH_SOCK`. `gh` uses its own sign-in, not an inherited `GH_TOKEN`, and gets `origin`'s URL without any credentials stored in it. The branch and worktree stay: the user merges on GitHub. The push sets the branch's upstream. On a Current checkout thread, which has no worktree or commit of its own, it pushes the branch the checkout has out, and refuses a detached HEAD (`prRefused`).
- **Linked pull requests** (PLX-318): `AgentRun.pullRequests` lists the web URLs of a run's pull requests, oldest first, stored with the run so they survive a restart. `agent/openPr` links the one it returns, and a tool call whose input contains `gh pr create` links each `https://github.com/<owner>/<repo>/pull/<n>` its output prints, whatever the backend. Each new link appends `agent.updated`. `pr/view` and `pr/act` run `gh` by the URL, as the user, in plxd's temp folder rather than a checkout, with Open PR's `ghUnavailable` and `prFailed`, and not through the run's actor, so a slow GitHub never holds up a running agent. They refuse a URL not linked to the run (`invalidParams`), so a client can't make plxd run `gh` on any other argument.
- **The Git menu** (RYA-298) works in the run's folder, its worktree or a Current checkout thread's checkout, through the run's actor. `agent/gitStatus` reads `git status --porcelain=v2 --branch` with no optional locks, so it answers while a run works and never takes the index lock from a turn's own git: the branch (null when detached), how many paths have uncommitted changes, untracked ones included, the upstream, and how many commits are ahead of it, or with no upstream, on none of `origin`'s branches, and whether there is an `origin`. `agent/commit` stages everything and commits with the message, as the identity the user's checkout configures, with no hooks or signing. In a worktree it is the run's commit, as a turn's end makes it (`agent.diffReady`), so Accept and Open PR take it. `agent/push` pushes the folder's branch from the user's checkout to `origin` with `--set-upstream`, as Open PR pushes. Both refuse a running run, and commit refuses when there is nothing to commit and push a detached HEAD (`gitRefused`). A commit git fails is `commitFailed` and a push `pushFailed`, each with git's stderr; a status git fails is `worktreeFailed`. Each answers with the status after it.
- **The user's own git setup** applies to Accept's git calls, which run in the user's checkout: global config, filters such as Git LFS's, merge drivers, and identity. The merged commit's `.gitattributes` decides which files go through which of the user's filters, and `.lfsconfig` can name the LFS server, exactly as when the user runs `git merge` themselves. No code the agent wrote runs that way, only the user's own filter programs, so this is accepted.
- **A failed checkout puts back only what git wrote.** `merge --ff-only` can stop part way, when one of those filters fails (a required LFS smudge that can't download) or when git can't move the branch after checking out. Minutes can pass between the overlap check and that failure, and the user, an editor, or another git can write files meanwhile. So plxd never restores from a stale check:
  - When git failed on `index.lock`, another git holds the index and git wrote nothing, so plxd refuses and changes nothing.
  - When the 5-minute timeout stopped git, git leaves `index.lock` behind. plxd changes nothing and says so, naming the lock and the files that may be partly updated. It doesn't remove the lock, because it can't tell it from a live one.
  - Otherwise, for each path the merge changes, plxd compares the working tree (hashed as `git add` would) with the merge's version and HEAD's. A file that still holds exactly the merge's version is put back, index and working tree, with `git restore --source=HEAD --staged --worktree`, `.gitattributes` first. A file the merge added is removed, along with folders left empty. A file that holds HEAD's version needs nothing. A file that holds neither was written by someone else, so it is left alone and named in the error.
  - Refusing up front whenever `.gitattributes` changes was rejected: agents edit it legitimately, and a failing filter doesn't need an agent to be involved.
- **No git call plxd makes runs a repository hook.** Every call in the user's checkout, including Accept, `worktree add`, `worktree remove`, `branch -D`, and `worktree prune`, runs with `-c core.hooksPath=/dev/null`, like the worktree-scoped calls (#166). Once a run is accepted, the checkout's hooks can include files the worker wrote, because `core.hooksPath` often names a tracked folder (husky). A `post-merge`, `post-checkout`, or `reference-transaction` hook would otherwise run the worker's code unsandboxed in plxd: on the merge, on the branch deletion right after it, or on the next `agent/start` (0013: review is the last gate). Someone who relies on a hook, such as a post-merge install, runs it themselves.

### The event log is stored

0007 moved the log to SQLite in M3. The `events` table holds every event with its daemon-wide `seq`, its project, and its run. `log_meta` holds `logId`. So `logId` and `seq` now survive a restart, and an editor resubscribes from its last `seq` instead of reloading. `events/subscribe` still replays only from the newest `retention` events in memory, now also bounded by bytes; `agent/events` reads a run's history from the table. The table is compacted on the retention policy in 0016 (#187): host and project events are pruned by count, and a run's events stay as long as its run row does (nothing prunes runs yet; see #207). `agent/events` pages are capped at about 4 MiB of event JSON as well as by count, and always hold at least one event, so a page fits in 0007's 8 MiB frame. Replay tolerates gaps in `seq`, whether from a pruned row or an event that failed to be stored; a failed store also clears the stored `logId` so the next start gets a new one and clients resync.

Appending is a dedicated writer thread's job (#190), separate from `events/subscribe`'s in-memory replay window and from `agent/events`'s own read connection: assigning a `seq`, writing it, and publishing it to memory all happen as one call on that thread, so a request task aborted mid-append (0007's lost-connection case) can never leave the counter and the table disagreeing. `agent/events` can therefore read a `seq` from the table a moment before the in-memory window (and `agent/list`'s `seq`) reaches it. Harmless: the editor merges by `seq`, and `events/subscribe` never reads the table directly.

### Agents' environment (#96, minimal)

- Agent CLIs, CLI detection, and worktree git commands share one environment, built from an allowlist of plxd's own: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG` and `LC_*`, `TERM`, `__CF_USER_TEXT_ENCODING`, the proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, in either case), and the CA variables (`SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`). A worker has network access and reads prompt-injectable content, so a token plxd was started with (`GITHUB_TOKEN`, `NPM_TOKEN`, `OPENAI_API_KEY`, `AWS_*`, a database URL) must not reach it (0013). A backend adds what its account needs on top, and the launcher adds `PLXD_DATA_DIR`.
- Every process plxd starts also loses the SSH session's variables, including `SSH_AUTH_SOCK`: workers can't push, and plxd makes every commit locally.
- A Claude worker's CLI gets its run's own temp folder as `CLAUDE_CODE_TMPDIR`, so its commands' `TMPDIR` is in it; its own `TMPDIR` stays plxd's (0013, RYA-130).
- `PATH` gets `~/.local/bin`, `~/.cargo/bin` (rustup's, RYA-126), `/opt/homebrew/bin`, `/usr/local/bin`, and the system folders appended where missing. Appending keeps the user's order; it only fills in what launchd or an SSH session left out.
- A Claude worker's Bash commands keep that `PATH` (RYA-126). Claude Code 2.1.283 runs each command with the user's `$SHELL -c`, and zsh reads `/etc/zshenv` and `~/.zshenv` even then, so startup files that set `PATH` outright replace it. nix-darwin's `/etc/zshenv` does this. Claude Code's shell snapshot would restore it, but the snapshot is in the configuration folder, which the worker sandbox makes unreadable (0013), so sourcing it fails silently. So for each worker the backend writes `export PATH='<the CLI's PATH>'${PATH:+:$PATH}` to a new file in the data folder's `tmp/`, with a random name and mode 0600, and passes its path as `CLAUDE_ENV_FILE`. Claude Code reads the file itself, outside the sandbox, and runs it before each Bash command. No worker's commands can read or write the file, and plxd deletes it once the CLI exits, or at the next `serve` start after a crash (RYA-130). Entries the startup files added stay, after plxd's.
- A Codex worker's commands keep it too (RYA-141). Codex 0.157.1 runs them with the user's shell from the password database, not `$SHELL`, and its shell snapshot, which would restore `PATH`, is off because it would also restore `CODEX_API_KEY` (0013). So for each worker the backend creates a folder in the data folder's `tmp/`, with a random name, and passes it to commands as `ZDOTDIR` (`shell_environment_policy.set`). Its `.zshenv`, which zsh reads right after `/etc/zshenv`, unsets `ZDOTDIR`, runs the user's `~/.zshenv`, and ends with the same `export PATH` line. `allow_login_shell=false` keeps `.zprofile` and `.zlogin` from running after it, which leaves the same startup files as a Claude worker's. The sandboxed zsh has to read the file, so the worker's commands can read it too. They can't write it or read another run's. plxd deletes it once the CLI exits, or at the next `serve` start after a crash (RYA-130).
- Capturing the login shell's `PATH` stays open on #96.

## Consequences

- The editor can drive a worker end to end: start, stream, message, cancel, list, and rebuild a transcript after a reconnect or a restart (#105, #157).
- A restart no longer changes `logId`. Tests that told plxd instances apart by `logId` use the serve pid.
- Cursor workers are refused until #123 sets `worker_sandbox`. Codex workers are refused on every OS until RYA-145 isolates their temp folder (RYA-153); after that they run on macOS (RYA-38), and elsewhere wait for RYA-133 (Linux) and RYA-24 (Windows).
- A worker's CLI that ignores `SIGINT` keeps a stopping plxd waiting for its cancel grace period, up to 15 s in total.
